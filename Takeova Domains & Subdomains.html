Custom Domains & Subdomains

How a Takeova site gets its address, how a merchant connects a domain they already own, and how a request on either host reaches the right site. It covers the backend, the infrastructure and the three frontend surfaces, and lists what is not built yet.

Read from takeova-backend and takeova-frontend source As of 9 Oct 2026 Environment: staging only (staging.takeova.ai)

01At a glance

Every site has exactly one platform subdomain. It can also have one custom domain. Cloudflare for SaaS handles certificates for custom domains, and one middleware in the api-gateway routes both kinds of host.

Custom domain1 per siteA single nullable column. It is globally unique, and there is no www/apex pairing.

02How a request finds a site

Subdomain and custom-domain traffic follow the same path. They differ at the edge, where the TLS certificate comes from, and in which lookup the gateway runs.

edge
Cloudflare
The takeova.ai zone, proxied. Custom hostnames terminate TLS here with a Cloudflare DV certificate. Sets cf-connecting-ip and cf-ipcountry.
aws
Express Mode ALB
A hand-added host rule for *.staging.takeova.ai and customers.takeova.ai. The wildcard ACM certificate is attached by SNI.
:3000
api-gateway
SiteHostMiddleware is registered first, before CORS, cookies and the Nest router.
rmq
tenant-service
GET_BY_HOST or GET_BY_CUSTOM_HOST. Checks that the site is published, the tenant is active, and (for a custom domain) the domain is ACTIVE.
pg
Rendered HTML
SitePage.renderedHtml, cached in Redis for 30 s. The gateway sets the CSP, injects scripts and emits analytics.
Where custom-domain traffic enters AWS

A merchant's domain is a CNAME to customers.takeova.ai. Cloudflare for SaaS sends that traffic to the origin with the merchant's own Host header. The ALB rule lists customers.takeova.ai, but a header like Host: shop.example.com matches neither rule value. It reaches the gateway through the listener's default forward action, which the reconciler Lambda keeps pointed at the live target group. This is inferred from the rule values and the reconciler. The Cloudflare fallback-origin and SSL-mode settings live only in the Cloudflare dashboard.

Paths on a tenant host

Once the gateway knows the site, it routes by path (site-host.middleware.ts serve()):

/site-assets/, /_forms/, /_sb/Normal Nest routesPass straight through. The exception is the /_sb/e and /_sb/c POST beacons, which are resolved by host. Same-origin form and chat posts skip CORS (the fix for the 2026-10-08 incident).
/portal…Reverse proxy → PORTAL_ORIGIN_URLAdds x-takeova-site: <label or full custom host>. The portal app keeps its own CSP.

03Subdomains

The subdomain is the site's permanent address. It keeps working after a custom domain is connected, and after one is removed.

How a site gets one

Onboarding

Assigned by the server in completeOnboarding. The user does not pick it.

  • The business name is slugified ([^a-z0-9]+ → -, at most 50 characters, falling back to site).
  • Candidates are slug, slug-1 … slug-49. Reserved names are skipped, and all candidates are checked in one query.
  • If none is free, the call throws SUBDOMAIN_ALLOCATION_FAILED. On a P2002 conflict the transaction is retried once.

Anonymous builder (marketing)

A build starts on preview-<suffix>. publishAnonymousBuild moves it to a real subdomain for 24 h (publishedUntil) and does not cost a credit.

  • Candidates are base, base-2…4 and base-<uuid8>.
  • A stricter rule applies here: 3–63 characters, no xn--, and a list of about 40 reserved labels.
  • When a user claims the build, the label moves to their site through a temporary claimed-<session> label.

Renaming

updateSiteSubdomain is available from the dashboard (Settings → Domain & site) and the editor (Site settings → Domains).

  • The value is trimmed and lowercased. Saving the current value does nothing.
  • Errors: SUBDOMAIN_RESERVED, SUBDOMAIN_TAKEN (from the P2002 unique violation), SITE_NOT_FOUND.
  • The old label is freed immediately, with no redirect. Cached copies of the old host expire within 30–60 s.

Validation

The gateway DTO, the tenant DTO and both frontend forms all use the same DNS-label pattern:

/^[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?$/   // 1–63 chars, no leading/trailing dash

No availability-check query exists. A user finds out the name is taken only after saving.

TLS for subdomains

An ACM wildcard certificate for *.staging.takeova.ai is attached to the Express Mode ALB listener by SNI, with Cloudflare proxied in front (proxied since 30 Sep 2026, confirmed by a cf-ray header). Multi-level labels such as a.b.staging.takeova.ai fail the label pattern and are not served. No certificate exists for bare *.takeova.ai yet.

04Custom domains

A merchant connects a domain they already own. Takeova does not sell or register domains, and it never touches the merchant's DNS.

The record the merchant adds

; one record, at the merchant's DNS provider
shop.example.com. 3600 IN CNAME customers.takeova.ai.
; apex (example.com) needs a provider that supports CNAME flattening / ALIAS. No A-record fallback is offered.

Connect flow

sequenceDiagram
    autonumber
    actor M as Merchant
    participant UI as Editor / Dashboard
    participant GW as api-gateway
    participant TS as tenant-service
    participant DB as Postgres
    participant CF as Cloudflare for SaaS
    M->>UI: Enter shop.example.com
    UI->>GW: setCustomDomain(siteId, domain)
    GW->>TS: RMQ tenant.sites.set-custom-domain
    TS->>TS: normalize + reject *.takeova.ai
    TS->>DB: claim domain, status PENDING
    TS->>CF: POST /custom_hostnames {ssl: http, dv}
    alt Cloudflare error
        TS->>DB: roll back all 5 columns
        TS-->>UI: CLOUDFLARE_REQUEST_FAILED
    else created
        TS->>DB: store cloudflareHostnameId
        TS-->>UI: {domain, PENDING, cnameTarget}
    end
    M->>M: Add CNAME at DNS provider
    loop every 2 minutes
        TS->>CF: GET /custom_hostnames/{id}
        TS->>DB: ACTIVE or FAILED, then email owner
    end
  1. Access check. assertSiteAccessible confirms the tenant owns the site and the team member's site scope covers it. The resolver also requires the STORE_SITES permission.
  2. Normalize. @IsFQDN() runs on both DTOs. The value is then trimmed and lowercased, a trailing dot is stripped, and it is converted to punycode with domainToASCII. The base domain and anything under it are rejected with CUSTOM_DOMAIN_NOT_ALLOWED.
  3. Provider check. If CLOUDFLARE_CNAME_TARGET, the token or the zone id is missing, the call fails with CUSTOM_DOMAIN_PROVIDER_NOT_CONFIGURED. These env vars are optional at boot, so the gap only shows up when a user tries to connect.
  4. Idempotent re-save. If the same domain is already stored with a hostname id, the call returns the current status and does nothing else. The UI blocks this too, because re-sending once disconnected a working domain.
  5. Claim, then register. The domain is written as PENDING first, so the unique index settles races (CUSTOM_DOMAIN_ALREADY_IN_USE). Then Cloudflare is called. If Cloudflare fails, all five columns are restored to their previous values.
  6. Swap. When domain A is replaced by B, A's Cloudflare hostname is deleted on a best-effort basis after B registers.
  7. Return. { domain, status: 'PENDING', cnameTarget }. The editor shows that cnameTarget; the dashboard shows its own hardcoded copy (see section 09).

Verification and status lifecycle

No DNS lookups happen. CustomDomainPollerService in tenant-service runs @Cron('*/2 * * * *'). It reads every PENDING row and asks Cloudflare for each one, in batches of 10. Rows within a batch run in parallel, and the batches run one after another. A failed Cloudflare read is logged and retried on the next run, and never marks a domain FAILED.

stateDiagram-v2
    direction LR
    [*] --> PENDING: setCustomDomain
    PENDING --> ACTIVE: CF status active AND ssl active
    PENDING --> FAILED: terminal SSL state, CF deleted, or older than 14 days
    PENDING --> [*]: removeCustomDomain
    ACTIVE --> [*]: removeCustomDomain
    FAILED --> [*]: removeCustomDomain
    note right of FAILED
        Dead end. Re-saving the same domain is a no-op,
        so the merchant must remove it and add it again.
    end note
    note right of ACTIVE
        Never re-polled.
    end note

// tenant-service/src/sites/custom-domain-classifier.ts
if (cfStatus === 'active' && sslStatus === 'active')      → ACTIVE
if (TERMINAL.has(sslStatus) || cfStatus === 'deleted')   → FAILED  // CLOUDFLARE_TERMINAL_FAILURE
if (now - requestedAt > 14 days)                         → FAILED  // STALE
otherwise                                                → UNCHANGED

TERMINAL = initializing_timed_out, validation_timed_out, issuance_timed_out,
           deployment_timed_out, deletion_timed_out, expired, deactivating, inactive

On each change of state the owner gets an email: "<domain> is now live on TAKEOVA" or "We couldn't verify <domain>". ACTIVE also stamps customDomainVerifiedAt. Cloudflare's specific failure reason is not stored. For details, support looks the hostname up in Cloudflare by the cloudflareHostnameId shown in admin.

Removing a domain

removeCustomDomain deletes the Cloudflare hostname on a best-effort basis (errors are logged and ignored) and always clears all five columns. The subdomain keeps serving. Neither the dashboard nor the editor asks for confirmation.

05Routing inside the gateway

apps/api-gateway/src/sites/site-host.middleware.ts decides whether a request is a tenant site before any other part of Nest runs.

Host classification, in order

  1. Subdomain. extractSubdomain(host, SITE_BASE_DOMAIN) strips the port and lowercases. The host must end in .staging.takeova.ai, the label must match the DNS-label pattern, and it must not be in RESERVED_HOSTS. A match is looked up with GET_BY_HOST, cache prefix site-host:.
  2. Custom-domain candidate. extractCustomDomainCandidate rejects bare IPs (ALB health checks), localhost, single-label hosts, the base-domain family and *.on.aws (the gateway's own Express host). What remains must match the FQDN pattern. It is looked up with GET_BY_CUSTOM_HOST, cache prefix site-custom-host:.
  3. Neither. next(): the request is ordinary API traffic (GraphQL, REST).

What tenant-service checks before returning HTML

06The canonical public host

One rule decides which address Takeova prints in links, emails and canonical tags: the custom domain if it is ACTIVE, otherwise <subdomain>.SITE_BASE_DOMAIN.

WhereImplementationUses it for
PublishSitePublishService.publicHost()<link rel=canonical>, hreflang URLs, the returned live URL, and the post-publish verifier fetch
Commercecommerce-service/src/customers/site-host.util.tsOrders, enrollments, booking cancellation, community, abandoned-cart and fulfilment emails
Checkoutcheckout/return-url.service.tsReturn-URL allowlist: the single public host, CUSTOMER_PORTAL_URL and the extra origins
Portal linksCustomersService.portalLoginUrlhttps://<host>/portal/login
Exceptionmember-messaging.service.ts tierJoinUrlalways uses the subdomain
Consequences of a single public host
  • Canonical tags are baked in at publish. If a domain becomes ACTIVE after the last publish, pages still point their canonical and hreflang tags at the subdomain until the merchant republishes. The poller does not trigger a re-render.
  • The subdomain is never redirected. Both hosts serve 200 with the same content. No 301 sends traffic to the custom domain.
  • Checkout started on the subdomain is refused once a domain is ACTIVE. The return URL must match the one public host. A test pins this on purpose ("replaces the subdomain host rather than adding to it").

07Data model

Domains belong to a Site (mine_sites), not to a tenant. A tenant with several sites has a subdomain per site and up to one custom domain per site.

09What users see

Three frontend surfaces cover domains. They were built at different times and disagree on several details.

Dashboard

Settings → Domain & site (DomainAndSitePanel), and Sites → overview (SiteDomainPanel). Both open CustomDomainSetup and SubdomainSetup.

  • Data comes from mySites, re-polled every 90 s. Changes are applied optimistically.
  • The CNAME target is hardcoded as customers.takeova.ai.
  • DNS Host field: the full domain.
  • Has no plan-cap check.

Editor

Site settings → Domains (DomainsTab, use-site-domains).

  • Re-reads from the server after every write, because Cloudflare and the poller own the status.
  • The CNAME target comes from the server (cnameTarget).
  • DNS Host field: always @, even for www.example.com.
  • Locks the row when the plan cap is 0. Footer button: "Verify & Save".

Admin

Sites list, site detail and its Domain tab. Read-only.

  • Filters: domain status and has-custom-domain. Search covers customDomain.
  • "Domains needing attention" = pending + failed.
  • Shows requested and verified times, how long a domain has been pending, and the Cloudflare hostname id.
  • The live-site link text always shows the subdomain, even when the link goes to the custom domain.

Client-side validation

// subdomain (dashboard + editor, mirrors the server DTO)
/^[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?$/

// custom domain (deliberately loose; the server's @IsFQDN and Cloudflare are the real checks)
/^(?:[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?\.)+[a-z]{2,}$/i     // max 253, http(s):// and trailing / stripped

Hardcoded hosts in the frontend

staging.takeova.ai is a display constant in mfe-dashboard/.../site-display.ts and mfe-admin/lib/format.ts, and the editor's last-resort fallback. The editor prefers the server's baseDomain, then the host from sitePublishStatus. NEXT_PUBLIC_SITE_BASE_DOMAIN exists, but its only consumer, resolveSitePublicHost, is never called in production code. The site switcher, Manage Websites dialog and door-access panel always show the subdomain, never the custom domain.

11CORS, CSP & trust

CORS

  • An exact-match allowlist, plus *.localhost outside production. Tenant hosts are never allowed: auth cookies are SameSite=None, so a wildcard would let one tenant's page make credentialed requests as a logged-in dashboard user.
  • Same-origin posts to /_forms/ and /_sb/ are exempt.
  • The frontend GraphQL proxy drops Origin so the portal works on tenant hosts.

CSP

  • Site-builder pages get a CSP built from the page itself: a sha256 hash per <style>, script-src 'none' when the page has no script, and embeds limited to YouTube-nocookie, Vimeo and Google Maps.
  • The store and legacy HTML use TENANT_SITE_CSP (Stripe, Google Fonts, frame-ancestors 'none').
  • /portal and /bio keep their upstream app's CSP.

Trust boundary

  • Visitor IP comes from cf-connecting-ip, and country from cf-ipcountry.
  • The origins (the ALB and *.amplifyapp.com) are not locked to Cloudflare. Anyone who calls the origin directly can forge these headers.
  • Presigned asset redirects send Cache-Control: private. Cloudflare once cached them on custom domains past their expiry.

13Known gaps

Ranked by how likely each one is to hurt a merchant or the business. Nothing in this flow has been tested end to end against a live gateway with a real domain (QA items D6 and E-14 are still open).

high

The plan cap is not enforced on the server

Starter tenants (cap 0) can connect a domain through the dashboard or the API. The fix is a decideCap check in setCustomDomain, the same pattern the other site-builder metrics use.

tenant-service/src/sites/sites.service.ts · setCustomDomain
high

The dashboard and editor give different DNS instructions

The dashboard says Host = the full domain, with a hardcoded target. The editor says Host = @ for every domain, so a merchant connecting www.example.com is told to put the CNAME on the apex. A CNAME at the apex also needs a provider that supports flattening. No A-record or ALIAS guidance exists.

DomainsTab.tsx · CustomDomainSetup.tsx · site-display.ts
high

updateSiteSubdomain skips permissions and site scope

It has no PermissionsGuard, and the service does not apply the team-member site scoping that assertSiteAccessible gives the custom-domain mutations. Any team member can rename any site's public address.

api-gateway/src/sites/sites.resolver.ts · sites.service.ts updateSubdomain
medium

FAILED is a dead end

Re-saving the same domain does nothing, and no re-check mutation exists. The failure email says to try connecting again, but the only way out is to remove the domain and add it again. ACTIVE domains are never re-polled either, so if Cloudflare later revokes a domain, Takeova doesn't notice.

sites.service.ts:367-369 · custom-domain-poller.service.ts
medium

Domain changes don't re-render pages or clear caches

Pages keep their subdomain canonical and hreflang URLs until the next publish. The subdomain is never 301-redirected to the custom domain, so two hosts serve the same content. A renamed subdomain's old label is freed at once, with no redirect.

site-publish.service.ts · site-render-cache.service.ts
medium

The origin is not locked to Cloudflare

The ALB and the Amplify origins accept direct traffic, so a direct caller can forge cf-connecting-ip and cf-ipcountry. Analytics, rate limits and anything else keyed on visitor IP inherit that.

visitor-ip.util.ts · PROPOSALS_QA_SIGNOFF.md:114
medium

Link in Bio is broken on custom domains and on staging

The bio lookup DTOs accept only a single DNS label and query only Site.subdomain, so a full custom host misses. MARKETING_ORIGIN_URL is not set in the staging deploy, so /bio on tenant hosts most likely 404s. That second point is inferred from the config, not checked live.

public-link-in-bio-page.input.ts · link-in-bio.service.ts
medium

Store cache key mismatch

The store router writes store-site:v4:<host>, but publish invalidation deletes store-site:<host>. Store pages only refresh when the 30 s TTL runs out.

public-store.router.ts · site-render-cache.service.ts:121-125
medium

tenant-service probably runs with the wrong base domain

The CloudFormation template sets no SITE_BASE_DOMAIN for tenant-service, so it falls back to takeova.ai. The editor's Domains tab may then show <sub>.takeova.ai on staging, and the "own domain" guard blocks all of takeova.ai. The second effect is stricter than needed but safe. Confirm against the live task definition.

backend-infra.yaml tenant-service task · sites.service.ts domainFacts
low

Poller robustness

The poller has no distributed lock, so two tenant-service replicas would both poll and email twice. The Cloudflare axios calls have no explicit timeout.

custom-domain-poller.service.ts · cloudflare-custom-hostname.client.ts
low

Edge config is not in code

Cloudflare DNS, the SaaS fallback origin, the SSL mode, the ACM certificate and the tenant ALB rule were all created by hand. A production stack on bare takeova.ai will have to be set up again from memory. infra/DEPLOYMENT.md also references files that no longer exist.

low

Consistency and polish

  • Three reserved-name lists that disagree.
  • No subdomain availability check.
  • Status labels differ across the surfaces.
  • Removing a domain has no confirmation step.
